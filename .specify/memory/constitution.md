# Free2Genius Constitution

**Project**: Free2Genius — a propensity-plus-agent growth system that decides *who* to
nudge toward a paid subscription (Genius) with an uplift model, and *what to say* with a
locally-hosted, evidence-grounded LLM agent.

**Domain**: Consumer fintech growth. Every decision in this repository touches a real
person's money, so the constitution below is weighted toward provable restraint rather
than maximum conversion.

---

## Core Principles

### I. Evidence Over Persuasion (NON-NEGOTIABLE)

The agent may state a number only if that number was returned by a tool reading this
user's own account data, or by the pricing catalog. No exceptions, no "approximately",
no arithmetic performed by the language model.

This is enforced mechanically, not requested politely: every tool result is walked and
its numeric values recorded, and every dollar figure in generated text is checked
against that ledger before a human sees it. A message containing an unaccounted number
is blocked, not logged and shipped.

Corollary, and the principle the whole product hangs from: **the agent must be able to
recommend against buying.** When estimated savings do not exceed the subscription price,
it says so. A growth system that cannot say "this is not worth it for you" is a
mis-selling engine with a nicer interface.

### II. Local-First Inference

Account data is scored and narrated by models running inside our own trust boundary.
The default runtime is a quantized open-weights model executed in-process; no user
attribute, transaction, or fee event crosses a network boundary to a third-party
inference provider in the default configuration.

Hosted frontier models are supported as an explicitly-configured escalation path only,
and the provider interface is the single seam where that choice is made. Choosing a
provider must never require touching agent logic, tools, or guardrails.

Rationale: in regulated consumer finance, "the data never left" is a shorter conversation
with a security reviewer than any data-processing agreement. It is also free to run,
which means the evaluation suite can execute on every commit.

### III. Uplift Over Propensity

We optimize the *incremental* effect of an intervention, not the probability of an
outcome. Targeting a user who would have converted anyway spends budget and buys
nothing; targeting a user whom contact actively annoys destroys value.

Therefore: models estimate a conditional average treatment effect; the targeting policy
consumes that effect, not a raw score; and the system must demonstrably *withhold*
contact from negatively-affected users ("sleeping dogs"). A policy that cannot be shown
to avoid harm is not shippable, regardless of its lift.

### IV. Guardrails Are Code, Not Prose

Any safety property stated in a specification must exist as an executable check that can
fail the build. Prompt instructions are mitigations, never controls. If a property
cannot be expressed as a test, the specification is rewritten until it can be.

### V. Every Goal Metric Ships With a Counter-Metric

No optimization target is accepted without a guardrail that detects the cheapest way to
game it. Conversion rate ships with 30-day retention. Targeting coverage ships with
fairness across income bands. Agent helpfulness ships with a grounding-violation rate.
A dashboard showing only the goal metric is considered incomplete work.

### VI. Reproducible by Default

Every artifact — dataset, model, metric, chart, evaluation verdict — regenerates from a
clean checkout with a documented command and a fixed seed. Generated artifacts are not
committed; the code that produces them is. If a number appears in a document, the
command that produced it appears beside it.

### VII. Spec-Driven Development

No implementation without a specification, a plan, and an enumerated task list, in that
order, under `specs/`. Specifications describe behaviour and success criteria without
naming technology; plans choose technology and justify it; tasks are the only unit of
work an implementer may pick up.

Every feature also carries an architecture record: a high-level design describing
components and their contracts, and a low-level design describing the modules,
signatures, data shapes, and failure paths. Documentation is a deliverable of the
feature, not a follow-up.

### VIII. Synthetic Data, Stated Plainly

All data in this repository is synthetic and generated by code under `f2g/data/`. No
proprietary, customer, or production data is used. Pricing and feature descriptions are
illustrative placeholders. Every document that could be mistaken for real analysis says
so in its opening lines. Overstating provenance is treated as a defect of the same
severity as a broken guardrail.

## Technology Constraints

- **Inference**: open-weights models (Qwen2.5 family, GGUF-quantized) executed via
  `llama.cpp` in-process, or through an OpenAI-compatible endpoint (vLLM, Ollama,
  LM Studio, TGI). A deterministic template provider MUST exist so that the full system,
  including its test suite, runs on a machine with no model weights and no network.
- **Tool calling MUST NOT depend on a vendor's native tool-use API.** Small open models
  emit malformed structured output regularly; the runtime is responsible for making tool
  calling reliable via constrained decoding, schema validation, and a bounded repair
  loop. Correctness is the runtime's job, not the model's.
- **Modelling**: gradient-boosted trees (LightGBM) for propensity and uplift. Preference
  for methods whose assumptions can be stated in one sentence and checked.
- **Service**: FastAPI, typed request/response models, SQLite for event capture.
- **Front end**: React + TypeScript + Vite, no server-side rendering.
- **Python**: 3.11+, standard library preferred over a new dependency.

## Quality Gates

A change is mergeable only when all of the following hold:

1. `pytest` passes.
2. The agent evaluation suite reports **zero grounding violations** on the golden case
   set. This gate is absolute; a violation is a release blocker, not a regression to
   triage later.
3. Any model change reports discrimination (AUC) and uplift (Qini) against the recorded
   baseline, and a drop beyond the documented tolerance is justified in the PR.
4. The fairness slice report is regenerated, and any widening of the targeting-rate gap
   across income bands is explained.
5. Documents affected by the change — spec, plan, HLD, LLD, model card — are updated in
   the same change, not deferred.

## Development Workflow

The GitHub Spec Kit cycle, per feature: `constitution` (once) → `specify` → `clarify`
→ `plan` → `tasks` → `analyze` → `implement` → `converge`.

Features are classified into domains (A: Data Foundation, B: Decision Intelligence,
C: Agentic Layer, D: Product Surface, E: Trust & Operations) and numbered sequentially.
The classification exists so that a reviewer can enter the repository at any tier and
find a self-contained, independently valuable slice.

Ordinarily each feature is developed on its own `NNN-short-name` branch. This repository
is built on a single designated branch, so feature isolation is expressed through the
`specs/NNN-*/` directories and per-feature commits rather than through branch topology.

## Governance

This constitution supersedes convenience. When a principle and a deadline conflict, the
principle wins and the scope shrinks.

Amendments require: a written rationale, the affected specifications updated in the same
change, and a version bump below. Principle I (Evidence Over Persuasion) and the
zero-grounding-violation gate may not be weakened by amendment — only strengthened.

Complexity must be justified. A plan that introduces a dependency, a service, or an
abstraction records why the simpler alternative was rejected in its Complexity Tracking
table.
