# Free2Genius — demo narration

The spoken script. Edit the prose here; the browser actions for each scene live in
`scenes.py`, matched by the scene id in the heading. A scene's video is stretched or
sped up to fit its narration, so changing the words here changes the pacing and
nothing breaks.

Blank lines separate sentences for subtitle timing. Keep sentences short — a long
sentence becomes one long subtitle.

## intro

Free2Genius is a decision system, not a chatbot.

It answers one commercial question: of the people using a free financial product,
which ones should be invited to a paid subscription, and what should we say to them?

Everything you are about to see runs on a laptop with no internet connection and no
API key. Every user, fee and price is synthetic, generated by a script in this
repository. It is not real customer data and the pricing is illustrative.

## problem

The naive version of this problem is a propensity model. Rank everyone by how likely
they are to subscribe, then contact the top slice.

That is the wrong question. Someone who was going to subscribe anyway does not need a
nudge, and contacting them spends budget to buy a conversion you already had.

What we actually want is uplift: the difference a contact makes to that person. The
people worth contacting are the persuadables, not the certainties.

## targeting

This is the targeting console, reading live from the Python service.

Twelve thousand candidates. Eighteen hundred and one selected for contact out of a
budget of twenty-four hundred slots — so the budget is not what is holding us back.

The binding constraint is value fit, and that is the most important thing on this
screen.

## valuefit

Value fit is a rule the system applies before any commercial consideration. Genius
costs forty-four dollars and ninety-seven cents over ninety days. If the fees we can
show we would have saved this person are worth less than that, we do not contact them.

Filtering to the suppressed rows shows the scale of it. Seven and a half thousand
people were removed by this rule alone.

Look at this row. The model says this person is highly persuadable — they probably
would subscribe if we asked. Their estimated saving is thirty-three dollars against a
forty-five dollar cost, so the subscription would leave them worse off, and the system
refuses to ask.

This is the uncomfortable part of the design and the part I would defend hardest. A
targeting system that only maximises conversions will find these people and convert
them. The suppression is deliberate.

## fairness

Two numbers watch for a policy that quietly serves one income band better than
another.

The eligible-rate gap is the difference that exists in the population before we do
anything. The policy-induced gap is the part we added — about a third of one percent.

Separating those matters. A system is not unfair because the world is uneven; it is
unfair when it widens the unevenness, and only the second number is ours to answer
for.

## concierge

Now the message. Picking a user moves to the concierge, which drafts the nudge that
person would receive.

Every monetary figure in this message is a clickable chip. That is the whole point of
this screen.

Clicking a number shows the tool call that produced it — the function, the arguments,
and the raw result the agent read.

A model claiming a number is grounded is an assertion. A number you can click to see
the account query behind it is evidence. If a figure has no provenance it renders
differently, so an ungrounded claim is visible rather than buried.

## guardrails

Under the message, the checks that ran on it before anyone would see it.

Numeric grounding: every figure traces to a tool result. Prohibited advice: no
investment or credit recommendations. Feature names: no inventing products that do not
exist. No pressure, coherence, and the required savings disclosure.

If a check fails, the draft is not shown. The system falls back to a templated writer
that is grounded by construction, and labels the message as degraded.

That fallback is a production runtime, not a test stub. A fresh clone of this
repository with no model weights serves correct, grounded messages — it just writes
them from templates instead of generating them.

## refusal

Some questions should not reach a model at all.

Asking whether to invest savings is a regulated advice question. The refusal happens
in a scope policy, before any model is loaded.

That ordering is the design. If you rely on the model to decline, you are trusting the
thing you cannot predict. Deciding in code means the refusal is testable and the same
every time.

## provider

The same agent runs on different inference backends. This dropdown picks which one the
next generation uses.

Deterministic is the templated writer — instant. Ollama runs a real open-weights model
on this machine, through an OpenAI-compatible endpoint, with the data never leaving the
network.

I am speeding this part up, because the real thing takes about a hundred seconds.

In that time the model is making five round trips: reading the account, listing recent
fees, fetching the feature catalogue, estimating the savings, then writing. Each tool
call is validated against a schema, and a malformed call is sent back with the specific
error rather than guessed at.

Same tools, same guardrails, same evidence chips. The provider is a configuration
choice, which is what makes the latency and the quality comparable across backends
instead of a matter of opinion.

Read the end of that message, though. Every figure is grounded — each chip still
traces to a tool call — but the conclusion contradicts them. The model read a
positive net position of seven dollars and sixty-two cents and called the
subscription not worth it.

I left that in. The guardrails check grounding, scope, pressure and disclosure. They
do not check reasoning, and a seven billion parameter model reasons like a seven
billion parameter model. That is the honest limit of this design, and it is the
single best argument for the deployment it was built for: batch drafting with a human
reviewing before anything is sent.

## experiment

Targeting and messaging are hypotheses. This tab is where they are tested.

Forty-five thousand users across three arms. The concierge arm converts at sixteen
point three percent, against fifteen point seven for a generic upsell and fifteen
point three for a holdout that was not contacted at all. The holdout is what separates
'the agent helped' from 'any nudge helped'.

Two intervals are shown for the same result. The fixed-horizon interval is only valid
if you look once, at the end, at a sample size you committed to in advance.

Nobody does that. People watch dashboards and stop when the result looks good, and
that habit inflates false positives badly.

The always-valid interval is wider, and it stays correct no matter how often you look.
Paying for that width is the honest trade.

Retention is a guardrail metric with a margin. A conversion win that costs retention
beyond the margin fails the verdict, regardless of how good the primary number looks.

## api

Nothing in the console is privileged. It is a React front end over a documented HTTP
service.

Scoring, cohorts, the agent, experiment assignment, and an audit endpoint that returns
every generation recorded for a given user.

One behaviour worth pointing out: if you explicitly ask for a provider that is not
available, the service returns a five-oh-three that names what is missing. It does not
quietly substitute a different model and let you believe you measured the one you
asked for.

## tradeoffs

What this system does not do, stated plainly.

Latency. A hundred seconds for a local generation is too slow for a live product
surface. It is fine for batch drafting with human review, which is the deployment this
is built for.

The data is synthetic, so the uplift numbers validate the pipeline, not the business
case. A real cohort would move them.

The in-process backend constrains generation with a formal grammar, so malformed tool
calls are impossible. The server backend cannot do that, so it relies on validation and
a repair loop instead. That difference is measured per backend rather than assumed.

And the fairness check is a monitor, not a constraint. It tells you the gap; it does
not optimise it away.

## close

Three things I would want to be judged on here.

The system declines to sell to people the product would not help, and the number of
them is on screen rather than in a footnote.

Every figure in a generated message is traceable to the query that produced it.

And the statistics match how people actually read dashboards, instead of assuming a
discipline nobody has.

The code, the specifications, the architecture decision records and the model card are
all in the repository.
