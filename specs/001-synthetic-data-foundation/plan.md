# Implementation Plan: Synthetic Data Foundation

**Feature**: `001` · **Date**: 2026-09-27 · **Spec**: [spec.md](spec.md) · **Status**: Implemented

## Summary

Generate two cohorts from an explicit structural causal model: a randomized **pilot** cohort
with observed outcomes and hidden true treatment effects, and an unlabelled **live** cohort for
serving. Expand each user's aggregate features into dated events that reconcile to the cent, and
centralise all pricing facts in one auditable module.

The design choice that carries the feature: **latent segments shape observable behaviour but are
never features.** The learner must recover effect heterogeneity from signals a real product
logs, which makes the modelling exercise genuine rather than a lookup.

## Technical Context

**Language/Version**: Python 3.11
**Primary Dependencies**: NumPy (RNG and vectorised draws), pandas (frames and CSV)
**Storage**: CSV under `data/`, gitignored, regenerated by command
**Testing**: pytest — reconciliation, determinism, leakage, distributional invariants

**Constraints**: No network, no external data, fully seeded
**Scale/Scope**: 60,000 pilot + 12,000 live; ledgers derived on demand for any user

## Technical approach

### Structural causal model

Written as an explicit generative chain rather than a fitted joint distribution, so every
dependency is inspectable:

```text
segment  ~  Categorical(persuadable .24, sure_thing .16, lost_cause .44, sleeping_dog .16)
X        ~  P(behaviour | segment)          # 26 observable features
p0       =  sigmoid(f(X) + segment_offset + noise)
tau      =  g(X, segment)                   # heterogeneous, clipped to keep p0+tau a probability
T        ~  Bernoulli(0.5)                  # randomised: this is what identifies tau
Y        ~  Bernoulli(p0 + tau*T)
R        ~  Bernoulli(h(value_fit, was_pushed))  |  Y = 1
```

`f` is a hand-specified linear index over engagement, direct deposit, fee burden and support
contacts. `g` makes effect largest where the nudge can *teach* something — real fees being paid,
plus enough engagement to act — and negative where contact is an irritation.

The `was_pushed` term in `h` is the subtle part: a user converted *because of* the nudge who has
poor value fit retains materially worse. That is the mechanism that makes the retention guardrail
informative instead of decorative.

### Ledger derivation

Aggregates are the model's view; events are the agent's view. They must agree.

Rather than store events, derive them from a generator seeded by `sha256(user_id)`. Stable
without storage, works for any user including ones invented at demo time. Reconciliation is
enforced by construction:

- Fee events: exactly `_instant_transfer_count_90d` events at $4.99 and
  `_overdraft_count_90d` at $34.00, so the sum is arithmetically forced.
- Subscriptions: merchant prices drawn then **rescaled** by
  `target_total / raw_total` so the detail matches the aggregate exactly.

### Catalog isolation

One module owns the monthly price, free-tier fee amounts, per-feature savings mechanics and the
required disclosure. Nothing else in the codebase may state a price. This is what makes
[ADR-007](../../docs/adr/ADR-007-numeric-grounding-ledger.md) auditable: one file for Legal to
review, one file to change when pricing moves.

## Project Structure

```text
f2g/
├── config.py               # paths, seeds, cohort sizes, model tiers
└── data/
    ├── schema.py           # NUMERIC / BINARY / CATEGORICAL / LABEL / ORACLE column groups
    ├── generate.py         # the SCM and the CLI entry point
    ├── accounts.py         # AccountRepository + build_ledger
    └── catalog.py          # the single source of pricing truth

tests/
├── test_data_generation.py # determinism, ATE consistency, segment separation
├── test_ledger.py          # reconciliation to the cent, stability, empty cases
└── test_no_leakage.py      # oracle and label columns absent from features
```

**Structure Decision**: Single package. The data layer is a library with one CLI entry point; no
service boundary is warranted and inventing one would be complexity without a need.

## Complexity Tracking

No constitutional violations. One deliberate design cost recorded:

| Choice | Why | Simpler alternative rejected because |
|---|---|---|
| Derive ledgers instead of storing them | Any user id works; nothing to keep in sync; no storage | Storing events for 72k users adds fixtures that can drift from aggregates — the exact bug the feature exists to prevent |
| Underscore-prefixed count columns in the frame | The ledger needs exact event counts to force reconciliation | Recomputing counts from dollar totals is lossy at boundaries and would let detail and aggregate disagree |
