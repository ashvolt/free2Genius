# Free2Genius

**A growth system where a model decides *who* to contact and a locally-hosted agent decides
*what to say* — and where both are built so they can say "not you" and "not worth it".**

> **All data here is synthetic**, generated by `f2g/data/generate.py`. No Albert data, customer
> data or production model was used. Pricing is an illustrative placeholder. Every number in
> this README is reproducible from a clean checkout with `make all`.

## The problem

Most free users never see why a paid tier is worth paying for, and generic upsell copy does not
help because it is generic. The obvious build is a propensity model — predict who will convert,
contact the top decile — and it is the wrong build twice over.

**It optimises the wrong quantity.** On this population, ranking by predicted conversion spends
**96.7%** of a 10% contact budget on users who were going to convert anyway, then books their
conversions as programme impact.

**It cannot decline.** Some users respond *negatively* to contact. Here they are the
fee-stressed, high-support-contact segment, at **−2.2 pp** uplift. A propensity model has no way
to express "do not contact this person"; it only knows "less likely".

## What this builds instead

| Decision | Owner | Signal |
|---|---|---|
| Who is *movable*? | Uplift model (X-learner) | Treatment effect estimated from a randomised pilot |
| Who *should* be moved? | Targeting policy | Effect, subject to budget, do-no-harm, fairness and **value fit** |
| What do we say? | Concierge agent | The user's own fee history, narrated under hard guardrails |

### The idea that ties them together

The agent's grounded savings estimate is a **hard constraint inside the targeting decision**,
not a check beside it. Before contacting anyone, the system computes from that user's own
90-day fee history what Genius would actually save them, and suppresses them if it does not
clear the subscription price — no matter how movable the model says they are.

The consequence is structural rather than aspirational: **the system cannot hit its conversion
target by pushing users who will not benefit**, because the honesty check sits inside the
decision. On the live cohort the gate is the *binding constraint*, suppressing 7,530 of 12,000
candidates and raising the mean estimated saving of contacted users from **$34.75 to $70.21**.

See [ADR-004](docs/adr/ADR-004-value-fit-gate.md).

## Three decisions worth arguing about

**Local open-weights inference, by default.** ([ADR-001](docs/adr/ADR-001-local-first-inference.md))
The agent reads transactions, advances and fee events. Running a 1.5–3B model in-process means
no financial attribute crosses a network boundary, and — the part that matters more — the
evaluation suite costs nothing to run, so the zero-grounding-violation gate can cover *every*
case on *every* commit. A metered API would have forced sampling, and a sampled safety gate is
not a gate.

**Reliability is the runtime's job, not the model's.** ([ADR-003](docs/adr/ADR-003-runtime-enforced-tool-calling.md))
Small models emit malformed tool calls constantly. Rather than accept that, tool calling is
enforced by a **GBNF grammar generated from the tool schemas**, so malformed JSON is
unrepresentable rather than handled. Enum parameters become literal alternatives — which means
a hallucinated product feature cannot be emitted at all. Then schema validation, then a bounded
repair loop that *raises* rather than returning a best guess.

**Grounding is a mechanism, not an instruction.** ([ADR-007](docs/adr/ADR-007-numeric-grounding-ledger.md))
Every number any tool returns is recorded in a per-session ledger. Every number in the draft
message must be in it. An unaccounted figure blocks the message and the turn degrades to a
templated writer that is grounded by construction. This is why a 1.5B model is safe to deploy
here: it *did* fabricate seven dollar figures in testing, and none of them could reach a user.

## Running it

### Prerequisites

| | |
|---|---|
| **Python 3.11+** | required — everything except the browser console (tested on 3.11 and 3.13) |
| **Node 18+** | only for the browser console |

Check Python is present before anything else. On Windows use the launcher, which is what the
official installer puts on PATH:

```powershell
py --version         # Windows
python3 --version    # macOS / Linux
```

If that fails, install Python 3.11 or newer:

- **Windows** — `winget install Python.Python.3.12`, or [python.org/downloads](https://www.python.org/downloads/)
  ticking **"Add python.exe to PATH"**. If Windows opens the Microsoft Store instead of running
  Python, turn off the aliases under *Settings → Apps → Advanced app settings → App execution
  aliases*.
- **macOS** — `brew install python@3.12`
- **Debian/Ubuntu** — `sudo apt install python3.12 python3.12-venv`

### Run

> This project lives on the branch **`claude/sleepy-clarke-2h5iey`**, which is currently the
> only branch on the remote. After cloning, make sure you are on it and up to date:
>
> ```bash
> git fetch origin && git checkout claude/sleepy-clarke-2h5iey && git pull
> ```

```bash
./run.sh setup     # macOS / Linux          run.bat setup     # Windows
./run.sh all       #                        run.bat all
./run.sh api       # :8000, OpenAPI at /docs
./run.sh web       # :5173   <- open this
./run.sh test      # 205 tests
```

The wrappers find a working interpreter for you. If you already know your Python command,
`python run.py <task>` (or `py run.py <task>` on Windows) is equivalent. Run with no arguments
to list every task. A `Makefile` with the same targets exists for anyone who prefers `make`.

To run the agent on a real local model rather than the deterministic writer, pick one of
two paths and then choose it from the provider dropdown next to **Regenerate** (nudge card)
or **Send** (chat) in the console's Concierge tab.

**Already running Ollama, LM Studio or vLLM** — nothing to download, it reuses the models
you have. Defaults assume Ollama:

```bash
ollama list                                 # pick any instruct model you already have
export F2G_OPENAI_MODEL=qwen2.5:7b          # default; set F2G_OPENAI_BASE_URL for non-Ollama
python run.py api
```

Then select **Ollama / local server** in the dropdown.

**In-process llama.cpp** — no server, but it downloads its own weights:

```bash
.venv/bin/pip install llama-cpp-python      # .venv\Scripts\pip on Windows
python run.py models                        # ~2.9GB of open weights
```

Either way generation takes 60-110 seconds — the latency gap recorded as unmet in
[spec 005](specs/005-concierge-agent-guardrails/spec.md). An explicitly chosen provider
fails with a 503 naming what it needs, rather than quietly falling back.

The system is fully functional without those weights: the deterministic provider is a
**production runtime**, not a test stub ([ADR-006](docs/adr/ADR-006-deterministic-provider.md)),
and the default provider falls back to it with a warning when no weights are present.

## How it was built

Spec-driven, using [GitHub Spec Kit](https://github.com/github/spec-kit). Nine features across
five domains, each with a specification, plan, task list, and high- and low-level design
documents. The register is at **[specs/README.md](specs/README.md)**; the governing principles
are in **[.specify/memory/constitution.md](.specify/memory/constitution.md)**.

Several specifications were **corrected by their own implementation** — those corrections are
recorded in place rather than quietly edited out, because they are the most honest part of the
record. Two examples:

- Spec 003 required the ungated selection to be a strict superset of the gated one. A test
  written from it failed against correct code: suppressing a low-benefit user frees a budget
  slot that backfills with the next eligible user. **The spec was wrong and the code was right.**
- Spec 002 anchored its success criterion to a 30% contact budget. Measurement showed the
  uplift advantage is strongly reach-dependent — +115% at 5%, +33% at 20%, −7% at 50% — so the
  operating budget moved to 20% on the evidence, and the budget sweep became a required output
  so the reach-dependence can never again hide behind one number.

## Limitations

Stated here rather than left to be found:

- The data is synthetic. Real behaviour is messier and effects are smaller.
- Uplift estimates assume the pilot was randomised. Observational data would need a
  propensity-of-treatment model whose error would propagate.
- No authentication, rate limiting or TLS. **Do not deploy this service.**
- No human review loop for generated messages; a real rollout needs one.
- Fairness is monitored on one axis (income band) because that is what this population offers.

The full list is in the [model card](docs/governance/MODEL_CARD.md).
